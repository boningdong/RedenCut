# Waveform Performance Design

## Status and delivery order

This design is the first implementation project in RedenCut's audio-performance work.

It replaces duration-proportional waveform rendering before the project adopts managed audio sources and decoded PCM caches.

The later managed-audio design is specified in [`2026-08-14-managed-audio-source-design.md`](2026-08-14-managed-audio-source-design.md).

## System definition

### Goal

Keep timeline waveform interaction responsive for hour-long audio by making renderer work proportional to visible pixels and visible tracks rather than source duration or cached peak count.

### Boundary

This project changes waveform presentation and waveform-data access inside the renderer.

It does not introduce project packages, copied media, PCM caches, new playback behavior, or FFmpeg import changes.

### Inputs

- Existing `PeakData` generated by the main process.
- Timeline clips containing source and output time ranges.
- Viewport width, scroll position, zoom, track height, and device-pixel ratio.
- Track color, selection, mute state, and current playhead state.

### Outputs

- One canvas waveform per visible clip or another equivalent bounded canvas composition.
- A ruler and waveform that update correctly after pan, zoom, resize, clip movement, and mute changes.
- Measurements proving that draw work is independent of total source duration for a fixed viewport.

## Confirmed current bottleneck

`ClipWaveform` currently slices the source peak array and creates one SVG `<rect>` for every selected peak.

The current peak density is approximately 190 values per second, so a one-hour clip can create roughly 684,000 React elements and DOM nodes.

Each track also maintains an invisible WaveSurfer instance even though RedenCut draws the visible per-clip waveform separately.

The existing design therefore performs work proportional to audio duration and duplicates waveform-rendering responsibilities.

## Audacity reference

Audacity stores waveform summaries at multiple sample scales and selects raw samples, 256-sample summaries, or 65,536-sample summaries according to zoom.

Its waveform data cache produces screen columns, and its bitmap cache renders fixed-width image tiles for only the requested viewport.

RedenCut should adopt the principles rather than the implementation:

- Choose data resolution according to pixels per second.
- Produce at most a small constant amount of data per visible pixel.
- Cache bounded visual units.
- Draw pixels into a bitmap surface instead of constructing one UI node per sample or peak.

## Architecture

### `WaveformDataProvider`

The renderer consumes waveform data through a narrow interface rather than reading `PeakData` directly inside React components.

```ts
interface WaveformDataProvider {
  readRange(request: WaveformRangeRequest): Promise<WaveformBucketRange>
}

type WaveformRangeRequest = {
  sourceStartSeconds: number
  sourceEndSeconds: number
  targetPixelWidth: number
  signal: AbortSignal
}

type WaveformBucket = {
  min: number
  max: number
}

type WaveformBucketRange = {
  buckets: WaveformBucket[]
}
```

The interface expresses the renderer's requirement in source time and target pixels without exposing storage layout.

### `LegacyPeakDataProvider`

The first implementation adapts existing `PeakData` to `WaveformDataProvider`.

At construction it performs one duration-proportional pass to convert positive magnitudes into symmetric min/max data and build in-memory 256-, 4,096-, and 65,536-sample summary levels.

That initialization cost is measured separately from interactive rendering.

For each viewport request it selects an appropriate level, reads only the requested source interval, and aggregates at most a small constant number of summaries per device pixel.

It must not return the original duration-sized peak slice.

This adapter allows the renderer fix to ship without waiting for the new binary waveform cache.

### `CanvasWaveform`

`CanvasWaveform` owns the canvas lifecycle and drawing only.

It receives a provider, source-time range, rendered size, color, and mute state.

On size, range, zoom, or provider changes it performs these steps:

1. Abort an obsolete request.
2. Request buckets for the current device-pixel width.
3. Ignore results from obsolete requests.
4. size the canvas backing store for the device-pixel ratio.
5. Clear and draw min/max vertical spans in one canvas operation.

The component does not read Zustand stores, perform filesystem access, control playback, or understand clips beyond its explicit props.

### `WaveformView`

`WaveformView` remains the timeline orchestrator.

It maps clips to source ranges and output positions, controls selection and dragging, and supplies waveform props.

It no longer constructs visible SVG peak elements or creates invisible WaveSurfer renderers.

The ruler remains custom because it already supports RedenCut's zoom-out behavior without depending on WaveSurfer.

## Rendering behavior

### Resolution selection

For a requested source range and target device-pixel width, the provider computes a source-peaks-per-pixel ratio.

Each output bucket combines all contributing peaks and preserves the negative and positive extents needed by the canvas renderer.

The legacy positive-amplitude cache cannot recover asymmetric minimum and maximum samples, so the adapter renders a symmetric waveform until the binary min/max cache becomes available.

### Visible work

The canvas request is bounded by the clip's rendered width, not by its full source duration.

If a clip extends beyond the scroll viewport, `WaveformView` supplies the visible intersection and the corresponding source-time interval.

The first implementation may keep one canvas per visible clip because the existing clip structure already defines isolated interaction and styling boundaries.

Canvas virtualization across a very large number of clips is deferred until measurement proves it necessary.

### Request cancellation

Every asynchronous range request receives an `AbortSignal`.

Rapid pan, zoom, resize, or clip movement aborts the previous request, and stale results cannot commit to the canvas.

### Playback independence

Canvas drawing remains independent of playback.

Playhead updates change only the playhead element and must not trigger waveform-data reads or redraw static waveform pixels.

## Error handling

An unavailable or invalid waveform range renders an empty waveform area without breaking clip interaction or playback.

The provider reports a concise diagnostic, while the component may retry after its inputs change.

Because existing peak files are regenerable caches, their absence is never treated as source-audio loss.

## Testing strategy

Implementation follows test-driven development, with each behavior beginning as a failing focused test.

Hard CI requirements include:

- Range-to-peak-index calculations at start, middle, and end boundaries.
- Aggregation preserves the maximum magnitude represented by each output bucket.
- Returned bucket count is bounded by target device-pixel width.
- Fixed viewport requests remain bounded for 10-minute and one-hour fixtures.
- Provider initialization is the only accepted duration-proportional renderer step in the legacy phase, and all later viewport requests use the in-memory levels.
- One-track and four-track fixtures scale with visible tracks rather than source duration.
- Obsolete requests are aborted and stale responses are ignored.
- Ten clips referencing one peak source do not duplicate the underlying source data.
- Playhead-only updates do not request or redraw waveform data.
- There are no SVG elements or other DOM nodes proportional to peak count.

## Performance verification

The reference workload is a one-hour, 48 kHz stereo source represented by ten clips, with one visible track and a 1,920-pixel viewport.

Machine-dependent thresholds run in a repeatable dedicated profiling fixture on a named reference configuration rather than ordinary CI.

The fixture defines device-pixel ratio, track height, zoom and pan trace, repetitions, cache state, percentile calculation, and raw metric artifacts.

Targets are:

- Cached warm-app first meaningful waveform canvas commit at or below 500 ms p95.
- Waveform draw callback at or below 8 ms p95.
- No more than 1% missed 60 Hz frames during the defined pan and zoom trace.
- A 16.7 ms draw is retained as a diagnostic ceiling rather than the preferred budget.
- Retained renderer heap growth from a 10-minute to one-hour source is no greater than 15% or 25 MiB, whichever allowance is larger, after stabilized garbage collection.
- Process-tree RSS is recorded because renderer heap omits native and AudioWorklet memory.
- Viewport request-to-visible-update latency and obsolete-request cancellation are recorded.

## Deferred work

- Binary multiresolution waveform storage.
- Project-managed media and PCM caching.
- PCM-backed playback.
- GPU or worker-based waveform rendering.
- Clip virtualization beyond evidence from the reference workload.
- RMS waveform display.

## Completion criteria

The waveform project is complete when the SVG and hidden WaveSurfer paths are removed, correctness and boundedness tests pass, the repository quality gate passes, and the reference profiling report meets or explicitly accounts for the approved targets.
